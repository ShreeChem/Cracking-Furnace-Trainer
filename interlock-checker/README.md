# Interlock Consistency Checker

> **All example data in this folder is SYNTHETIC – FOR TRAINING ONLY.** It is invented,
> based on no real plant, and must not be used for design, operation or SIL verification.

A small Python tool that compares a **P&ID** (as a DEXPI file) with a **cause-and-effect
(C&E) matrix** (as Excel) and writes a list of mismatches, each with a severity, a
plain-language explanation and a suggested action.

Think of it as a desk-top loop check before the real trip test: it does not prove a
trip works, but it catches paperwork gaps that would otherwise surface during
commissioning, an audit or an incident review. Typical examples are a trip on the C&E with
no transmitter on the P&ID, a SIL-rated transmitter nobody connected to a trip, or a valve
that fails open when the trip needs it closed.

This folder is separate from the furnace trainer. It does not touch `index.html`, `src/`,
`tools/build.py` or `tests/engine-test.js`, and it has its own CI workflow
(`.github/workflows/interlock-checker.yml`) that runs only when this folder changes.

New to Python? Read **[GUIDE.md](GUIDE.md)**. It walks through the code step by step in the
order it was built and explains each part in plant terms.

## Quick start

You need Python 3.12 or newer (pyDEXPI needs it).

```bash
cd interlock-checker
```

```bash
python -m pip install ".[test]"
```

Run the checker on the synthetic furnace example:

```bash
python -m interlock_checker --pid examples/synthetic_furnace_pid.xml --ce examples/synthetic_furnace_ce.xlsx --rules rules/rules.yaml --out examples/output
```

It writes `interlock_report.xlsx`, `interlock_report.md` and `interlock_report.html` to the
`--out` folder and prints a one-line summary. The committed sample report is in
[`examples/output/`](examples/output/interlock_report.md).

| Option | Meaning |
|---|---|
| `--pid` | P&ID as DEXPI Proteus XML (`.xml`) |
| `--ce` | C&E matrix (`.xlsx`) |
| `--rules` | settings and latching/reset rules (`.yaml` or `.json`). Optional: without it, checks 1–3 run with default settings and check 4 is skipped |
| `--out` | folder for the reports (default `output`) |
| `--sheet` | C&E sheet name, if the reader should not find it by itself |
| `--fail-on HIGH` | exit code 1 if any finding is HIGH (or MEDIUM, LOW, INFO: that level or worse). Useful in CI |

Exit codes: `0` = report written; `1` = findings at or above `--fail-on`; `2` = an input
could not be read (the message says why).

To regenerate the synthetic input files:

```bash
python -m interlock_checker.synthetic --out examples
```

## Inputs

### 1. P&ID (DEXPI)

[DEXPI](https://dexpi.org/) is the vendor-neutral exchange format for P&IDs; most P&ID tools
can export it as "Proteus XML". The tool reads it with **pyDEXPI** and collects:

- equipment tags (furnace, fans, pumps, drums);
- instrument loops, with their transmitter tags, **safety class** (e.g. `SIL2`) and **voting**;
- valve tags with their **fail position** (FC / FO / FL) from the actuator.

If the file cannot be read, the tool stops with a clear message (file missing, not XML, not
DEXPI, or no tagged items in it). If pyDEXPI loads the file but reports lost data, those
messages are printed and added to the report as "Reader warnings".

Tags are matched ignoring case, spaces, hyphens, underscores and slashes, so `FZT-101A`,
`fzt 101a` and `FZT_101A` are the same tag.

**Synthetic furnace P&ID**: `examples/synthetic_furnace_pid.xml`. The public DEXPI examples
contain no ethane-furnace tags, so this file was generated by
`interlock_checker/synthetic.py`. It is hand-written Proteus XML that follows the structure
of the DEXPI reference P&ID, because the pyDEXPI 1.2 exporter only writes equipment and
metadata, not instruments. It is read back through pyDEXPI's normal parser like any other
DEXPI file.

**Public DEXPI example**: to show the reader works on a real DEXPI file, the tests also read
the DEXPI e.V. reference P&ID `C01V04-VER.EX01.xml`, as shipped in the pyDEXPI repository.
It is **not committed here**, because its redistribution terms are not stated. It is
downloaded from a pinned pyDEXPI commit:

```bash
python scripts/fetch_public_example.py
```

The test that uses it is skipped if the file is missing. CI downloads it first, so in CI the
test always runs.

### 2. Cause-and-effect matrix (Excel, IEC 62881 style)

`examples/synthetic_furnace_ce.xlsx`. Every sheet is stamped "SYNTHETIC – FOR TRAINING
ONLY" in cell A1 and in the print header and footer.

- **Rows = causes**: Cause ID, Initiator tag, Description, Trip setpoint, Units, Trip type,
  Voting (e.g. `2oo3`), SIL, **Latching**, **Reset**, Notes.
- **Columns = effects**: above the cause headings, five label rows give Effect ID, Final
  element tag, Description, Action on trip (CLOSE / OPEN / STOP) and Required safe position.
- **Intersections**: `X` means "use the column's action". An action word (e.g. `OPEN`)
  overrides it for that cause.

The reader finds the headings by their text, not by fixed cells, and accepts common
alternative names (e.g. "Tag", "Setpoint", "Remarks"). See `CAUSE_COLUMNS` and
`EFFECT_LABELS` in `interlock_checker/ce_reader.py`.

### 3. Rules file

`rules/rules.yaml` holds the settings for checks 2 and 3 and the latching/reset rules for
check 4. It is written so a non-programmer can edit it. See GUIDE.md, Step 6.

## The checks

| # | Check | Default severity | Why it matters |
|---|---|---|---|
| 1 | Tag in the C&E (initiator or final element) **missing from the P&ID** | HIGH | The trip may exist only on paper, or the P&ID was not updated after an MOC. |
| 2 | **Trip transmitter on the P&ID with no C&E row**: a transmitter whose tag matches a configurable pattern (default: ISA `Z` letter, e.g. `PZT`, `BZS`), or that carries a safety class such as `SIL2` | HIGH | A trip is missing from the C&E, or the P&ID marks the instrument wrongly. |
| 3 | **Valve fail position contradicts the trip action**: CLOSE on a fail-open valve, OPEN on a fail-close valve | HIGH | On loss of air or power the valve goes the wrong way. |
| 3 | Trip action on a **fail-last (FL)** valve | MEDIUM | It only trips while the actuator still has energy; not fail-safe. |
| 3 | Trip action on a valve with **no fail position** on the P&ID | LOW | The fail-safe direction cannot be checked. |
| 4 | **Latching / reset rules** from the rules file | set per rule | Placeholder rules for now: your site rules go here. |

Check 3 also notes when the C&E disagrees with itself: an intersection says OPEN while the
column's required safe position says CLOSED.

## Seeded mismatches in the synthetic example

The synthetic trips follow the furnace in this repository's trainer (`src/engine.js`): pass
flow low-low, steam/ethane ratio low-low, COT high-high, arch O2 low-low, firebox pressure
high-high and steam drum level low-low. Four typical furnace trips the trainer does not
model were added: fuel gas pressure low-low, flame failure, tube metal temperature (TMT)
high-high and a manual emergency shutdown button. All values are invented.

Mistakes were planted on purpose so that every check has something to find. Each one is
marked `SEEDED` in `interlock_checker/synthetic.py`. A clean variant
(`*_clean.xml` / `*_clean.xlsx`) fixes them all and gives **zero findings**.

| # | Check | Tag | What was planted |
|---|---|---|---|
| 1 | 1 | TZT-160 | TMT high-high trip is on the C&E, but the transmitter is not on the P&ID (as if added after a HAZOP with the MOC not closed). |
| 2 | 1 | XV-176 | Pilot gas second shutoff valve is a C&E effect but is missing from the P&ID. |
| 3 | 2 | FZT-101D | Pass D low-low flow transmitter is on the P&ID (SIL1, `Z` tag), but the C&E has rows only for passes A–C. |
| 4 | 2 | PT-172 | Fuel gas pressure high-high transmitter is marked SIL2 on the P&ID but has no C&E row. Its tag has no `Z`, so only the SIL marking reveals it. |
| 5 | 3 | FV-110 | Dilution steam valve: the C&E says OPEN (keep steam on the coils), but the P&ID shows it fail-close. |
| 6 | 3 | XV-172 | Fuel gas vent (bleed) valve: the C&E says OPEN, but the P&ID shows it fail-close. |
| 7 | 3 | TV-150 | COT high-high row says OPEN on the fail-close fuel gas control valve; the column's safe position is CLOSED. |
| 8 | 3 | XV-100 | Ethane feed shutoff valve drawn fail-last (FL) while the C&E needs CLOSE. MEDIUM. |
| 9 | 4 (R-PH-01) | PZT-141 | Firebox pressure high-high closes the fuel gas shutoffs but is not latched. |
| 10 | 4 (R-PH-02) | FZT-110 | Steam/ethane ratio low-low is a SIL2 trip with AUTO reset. |
| 11 | 4 (R-PH-03) | BZS-171 | Flame failure is SIL2 with 1oo1 voting. MEDIUM. |

Result: **11 findings (9 HIGH, 2 MEDIUM)**. The end-to-end test checks that exactly these 11
are found.

## Latching and reset rules: waiting for your definitions

The three rules in `rules/rules.yaml` are **placeholders**, not a recommendation:

- `R-PH-01`: every trip of a fuel gas shutoff valve must be latched with manual reset;
- `R-PH-02`: no auto-reset on any SIF;
- `R-PH-03`: SIL 2 and higher trips must not use 1oo1 voting.

Each is marked `placeholder: true`. In the report they appear as
"[PLACEHOLDER RULE – replace with your own]", and the summary lists placeholders still in
use. To add your own rules, follow GUIDE.md, Step 6. Copy the template at the bottom of the
file and fill in `when` (which C&E rows) and `require` (what must be true). No Python is
needed for rules that test C&E columns. If a rule needs a new kind of test, one small
function is added to `OPERATORS` in `interlock_checker/rules.py`.

## Tests

```bash
python -m pytest --cov --cov-report=term-missing
```

- unit tests per check, including a clean case that gives zero findings;
- parsing tests for the C&E reader (layout, alternative headings, every error message) and
  the P&ID reader (synthetic file, public DEXPI example, broken and non-DEXPI files);
- rule framework tests (every test operator, every rules-file mistake message);
- end-to-end tests on the synthetic example (all 11 seeded mismatches found, clean variant
  gives zero, CLI exit codes, all three report formats).

Last local run: **88 passed, 99 % line coverage** (Python 3.13, pyDEXPI 1.2.0). CI runs the same
suite on Python 3.12 and 3.13 and fails below 80 % coverage.

## Known limits and open points

- **Latching/reset rules are placeholders** until you supply your own (see above).
- Latching and reset are read **per cause row**. Some C&Es put reset per effect (e.g. local
  reset at a valve); that layout is not read yet.
- Voting and SIL are read from both the P&ID and the C&E, but **not compared with each
  other**. That would be an easy extra check if you want it.
- Trip transmitters are recognised by tag pattern or safety class. A P&ID that marks
  neither will not trigger check 2. Adjust `trip_transmitter_patterns` to your tagging
  standard.
- Check 3 knows CLOSE→FC and OPEN→FO (editable in `settings`). Motor actions such as STOP
  are not compared, because motors have no fail position on the P&ID.
- Only DEXPI **Proteus XML** is read, and drawing graphics are ignored. P&IDs that are only
  PDFs or images cannot be read.
- Tested against pyDEXPI 1.2.0. pyDEXPI is young and its API may change; the version is
  pinned to `>=1.2,<2`.
